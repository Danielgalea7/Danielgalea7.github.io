Segmentación RFM de clientes

Curso 3 · lab

Marketing de TheLook eCommerce quería campañas por tipo de cliente porque la retención había caído.

Peso de cada segmento

% de clientes frente a % de ingresos · 12 meses a sep-2026

Clientes
Ingresos
  • High Value 29 % · 52 %
  • Loyal 21 % · 7 %
  • Persuadable 22 % · 18 %
  • At Risk 15 % · 12 %
  • Other 13 % · 11 %
Qué hice
Calculé recencia, frecuencia y valor monetario con CTEs, los repartí en cuartiles con NTILE y asigné segmentos con CASE. Corregí tres fallos del enunciado: la frecuencia contaba artículos y no pedidos, la recencia estaba invertida y faltaba un ELSE.
Resultado
Con los datos públicos de los últimos 12 meses (28.025 clientes): el segmento High Value es el 29 % de los clientes y genera el 52 % de los ingresos; el 82 % solo compró una vez.
Lo que me llevo
NTILE reparte los empates al azar: 9.094 clientes con un solo pedido acababan en los cuartiles «altos» de frecuencia. Para variables con muchos empates uso umbrales (1, 2, 3+ pedidos).
Ver el SQL clave
WITH rfm_calc AS (
  SELECT
    o.user_id AS customer_id,
    DATE_DIFF(CURRENT_TIMESTAMP(), MAX(o.created_at), DAY) AS recency,
    COUNT(DISTINCT o.order_id) AS frequency,   -- fix 1: orders, not items
    ROUND(SUM(oi.sale_price)) AS monetary
  FROM `thelook_ecommerce.orders` o
  INNER JOIN `thelook_ecommerce.order_items` oi
    ON o.order_id = oi.order_id
  GROUP BY customer_id
),
rfm_quant AS (
  SELECT
    customer_id,
    NTILE(4) OVER (ORDER BY recency DESC) AS recency_quantile,  -- fix 2: 4 = most recent
    NTILE(4) OVER (ORDER BY frequency) AS frequency_quantile,
    NTILE(4) OVER (ORDER BY monetary) AS monetary_quantile
  FROM rfm_calc
)
SELECT
  customer_id,
  CASE
    WHEN monetary_quantile >= 3 AND frequency_quantile >= 3 THEN "High Value Customer"
    WHEN frequency_quantile >= 3 THEN "Loyal Customer"
    WHEN recency_quantile <= 1 THEN "At Risk Customer"
    WHEN recency_quantile >= 3 THEN "Persuadable Customer"
    ELSE "Other"                                                -- fix 3: no NULL segment
  END AS customer_segment
FROM rfm_quant;

Pipeline SQL con stored procedure

Curso 3 · lab

Logística necesitaba saber a qué distancia está cada cliente de su centro de distribución más cercano, y poder recalcularlo sin repetir pasos a mano.

Qué hice
Definí los esquemas, convertí coordenadas en GEOGRAPHY con ST_GEOGPOINT, calculé la distancia mínima con ST_DISTANCE en una subconsulta escalar y empaqueté la carga en un stored procedure que se lanza con un CALL.
Resultado
Seis sentencias manuales convertidas en un procedimiento reejecutable y programable, y una distancia por cliente lista para decidir dónde abrir o mover centros.
Lo que me llevo
Detecté que el CREATE OR REPLACE … AS SELECT del enunciado descartaba el esquema definido antes (y con él distribution_center_id); con INSERT INTO … SELECT se respeta.
Ver el SQL clave
CREATE OR REPLACE PROCEDURE `thelook_ecommerce.sp_create_load_tables`()
BEGIN
  -- centers: public table + geography transformation
  CREATE OR REPLACE TABLE `thelook_ecommerce.centers` AS
  SELECT id, name, latitude, longitude,
         ST_GEOGPOINT(dcenters.longitude, dcenters.latitude) AS point_location
  FROM `bigquery-public-data.thelook_ecommerce.distribution_centers` AS dcenters;

  -- customers, product_orders_fulfillment: same pattern ...
END;

CALL `thelook_ecommerce.sp_create_load_tables`();

-- distance (km) from each customer to the closest distribution center
SELECT
  customers.id AS customer_id,
  (SELECT MIN(ST_DISTANCE(centers.point_location, customers.point_location)) / 1000
   FROM `thelook_ecommerce.centers` AS centers) AS distance_to_closest_center
FROM `thelook_ecommerce.customers` AS customers;

Particionado: 50 veces menos datos por consulta

Curso 2 · lab

Un dashboard de TheLook sobre viajes en taxi cerca de las tiendas iba lento y costaba demasiado.

Datos escaneados por consulta

Tabla taxi_trips particionada por día · caché desactivada

  1. Sin filtro de partición≈489 MB
  2. Filtro > 2022-11-01≈10 MB
  3. Filtro > 1900-01-01≈489 MB
Qué hice
Comparé la misma consulta con y sin filtro sobre la columna de partición (pickup_datetime), desactivando la caché para medir bien los bytes procesados.
Resultado
De ≈489 MB a ≈10 MB por consulta (−98 %). En BigQuery bajo demanda se paga por bytes leídos, así que es también un 98 % menos de coste por consulta.
Lo que me llevo
LIMIT no ahorra nada, y un WHERE que no descarta particiones tampoco. Lo que ahorra es filtrar por la columna de partición.
Ver el SQL clave
-- No partition filter: scans the whole table (~489 MB)
SELECT * FROM `thelook_gcda.taxi_trips`
ORDER BY pickup_datetime DESC
LIMIT 100;

-- Filter on the partitioning column: only Nov-Dec 2022 partitions (~10 MB)
SELECT * FROM `thelook_gcda.taxi_trips`
WHERE pickup_datetime > '2022-11-01'
ORDER BY pickup_datetime ASC;
