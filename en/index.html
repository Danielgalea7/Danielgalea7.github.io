RFM customer segmentation

Course 3 · lab

TheLook eCommerce's marketing lead wanted campaigns per customer type because retention had dropped.

Share of each segment

% of customers vs % of revenue · 12 months to Sep 2026

Customers
Revenue
  • High Value 29% · 52%
  • Loyal 21% · 7%
  • Persuadable 22% · 18%
  • At Risk 15% · 12%
  • Other 13% · 11%
What I did
I computed recency, frequency and monetary value with CTEs, split them into quartiles with NTILE and assigned segments with CASE. I fixed three bugs in the brief: frequency counted items instead of orders, recency was inverted and the CASE had no ELSE.
Result
On the last 12 months of public data (28,025 customers): the High Value segment is 29% of customers and drives 52% of revenue; 82% bought only once.
Takeaway
NTILE splits ties arbitrarily: 9,094 one-order customers ended up in the 'high' frequency quartiles. For heavily tied variables I use thresholds (1, 2, 3+ orders).
Show the key SQL
WITH rfm_calc AS (
  SELECT
    o.user_id AS customer_id,
    DATE_DIFF(CURRENT_TIMESTAMP(), MAX(o.created_at), DAY) AS recency,
    COUNT(DISTINCT o.order_id) AS frequency,   -- fix 1: orders, not items
    ROUND(SUM(oi.sale_price)) AS monetary
  FROM `thelook_ecommerce.orders` o
  INNER JOIN `thelook_ecommerce.order_items` oi
    ON o.order_id = oi.order_id
  GROUP BY customer_id
),
rfm_quant AS (
  SELECT
    customer_id,
    NTILE(4) OVER (ORDER BY recency DESC) AS recency_quantile,  -- fix 2: 4 = most recent
    NTILE(4) OVER (ORDER BY frequency) AS frequency_quantile,
    NTILE(4) OVER (ORDER BY monetary) AS monetary_quantile
  FROM rfm_calc
)
SELECT
  customer_id,
  CASE
    WHEN monetary_quantile >= 3 AND frequency_quantile >= 3 THEN "High Value Customer"
    WHEN frequency_quantile >= 3 THEN "Loyal Customer"
    WHEN recency_quantile <= 1 THEN "At Risk Customer"
    WHEN recency_quantile >= 3 THEN "Persuadable Customer"
    ELSE "Other"                                                -- fix 3: no NULL segment
  END AS customer_segment
FROM rfm_quant;

What I did

# order_items.view
measure: total_revenue {
  type: sum
  sql: ${sale_price} ;;
}

# fixed: reference fields with ${} and avoid dividing by zero
measure: revenue_per_user {
  type: number
  sql: ${total_revenue} / NULLIF(${users.total_users}, 0) ;;
}

# model file
explore: order_items {
  join: users {
    relationship: many_to_one
    sql_on: ${users.id} = ${order_items.user_id} ;;
  }
}

SQL pipeline with a stored procedure

Course 3 · lab

Logistics needed the distance from every customer to their closest distribution centre — and a way to recompute it without manual steps.

What I did
I defined the schemas, turned coordinates into GEOGRAPHY with ST_GEOGPOINT, computed the minimum distance with ST_DISTANCE in a scalar subquery and wrapped the load in a stored procedure triggered by a single CALL.
Result
Six manual statements turned into one re-runnable, schedulable procedure, and a per-customer distance ready to decide where to open or move centres.
Takeaway
I noticed the brief's CREATE OR REPLACE … AS SELECT silently discarded the schema defined just before (losing distribution_center_id); INSERT INTO … SELECT keeps it.
Show the key SQL
CREATE OR REPLACE PROCEDURE `thelook_ecommerce.sp_create_load_tables`()
BEGIN
  -- centers: public table + geography transformation
  CREATE OR REPLACE TABLE `thelook_ecommerce.centers` AS
  SELECT id, name, latitude, longitude,
         ST_GEOGPOINT(dcenters.longitude, dcenters.latitude) AS point_location
  FROM `bigquery-public-data.thelook_ecommerce.distribution_centers` AS dcenters;

  -- customers, product_orders_fulfillment: same pattern ...
END;

CALL `thelook_ecommerce.sp_create_load_tables`();

-- distance (km) from each customer to the closest distribution center
SELECT
  customers.id AS customer_id,
  (SELECT MIN(ST_DISTANCE(centers.point_location, customers.point_location)) / 1000
   FROM `thelook_ecommerce.centers` AS centers) AS distance_to_closest_center
FROM `thelook_ecommerce.customers` AS customers;

Partitioning: 50× less data per query

Course 2 · lab

A TheLook dashboard on taxi drop-offs near stores was slow and too expensive.

Data scanned per query

taxi_trips table partitioned by day · cache disabled

  1. No partition filter≈489 MB
  2. Filter > 2022-11-01≈10 MB
  3. Filter > 1900-01-01≈489 MB
What I did
I compared the same query with and without a filter on the partitioning column (pickup_datetime), with the cache disabled to measure bytes processed properly.
Result
From ≈489 MB to ≈10 MB per query (−98%). With on-demand BigQuery you pay per byte read, so it's also 98% less cost per query.
Takeaway
LIMIT saves nothing, and neither does a WHERE that prunes no partitions. Filtering on the partition column is what saves.
Show the key SQL
-- No partition filter: scans the whole table (~489 MB)
SELECT * FROM `thelook_gcda.taxi_trips`
ORDER BY pickup_datetime DESC
LIMIT 100;

-- Filter on the partitioning column: only Nov-Dec 2022 partitions (~10 MB)
SELECT * FROM `thelook_gcda.taxi_trips`
WHERE pickup_datetime > '2022-11-01'
ORDER BY pickup_datetime ASC;
